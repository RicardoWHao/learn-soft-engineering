# 01 静态站点生成（SSG）与 VitePress 定位
> 本页是全树入口，先用 What / Why / How / When 四问把 VitePress 讲清楚，明确它与 SSG 的关系，并厘清 Vite / VitePress / VuePress 三个易混名字各自的定位；随后把 SSG 放进 SPA/SSR 的坐标系，回答「为什么文档站应该用静态生成」以及同类工具的选型差异。
**前置依赖**：无，本知识树的起点
**适用版本**：VitePress 稳定线 `1.6.4`（2.x 尚处于 alpha，本知识树以 1.x 为基线）；1.x 可在 Node 18+ 运行，官方文档当前建议 Node.js 22+。
---
## 一、先用 What / Why / How / When 认识 VitePress
| 问题 | 结论 |
| --- | --- |
| What（是什么） | Vue 团队官方出品的**静态站点生成器**：用 Markdown 写内容，构建时把每个 md 编译成 Vue 组件并预渲染为纯静态 HTML/CSS/JS，交付一个没有后端的网站 |
| Why（为什么用） | 文档/知识库**读多写少、变更只在作者发布时发生**，把渲染从「每次请求」挪到「每次发布」只做一次，换来免服务器、首屏极快、SEO 友好、可免费托管 |
| How（怎么做到） | 站在构建工具 Vite 与框架 Vue 3 之上：dev 时 Vite 起本地服务即时编译，build 时走 Markdown→Vue 组件→服务端预渲染，浏览器再水合（详见子模块 04） |
| When（何时用） | 技术文档、知识库、博客、产品手册等**内容型站点**；不适合强登录态、按用户返回不同内容、或秒级变化的实时数据应用 |
一句话版本：**VitePress 让你只写 Markdown，却能得到一个带搜索、主题、组件化能力且可秒开的现代网站，且不需要任何服务器。**
## 二、VitePress 和 SSG 是什么关系
这是最容易混淆的一点，必须先厘清：**SSG 是一类架构范式，VitePress 是这个范式的一个具体实现工具**，二者是「方法论与产品」的关系，不是并列、也不是可以二选一的两个同类。
- **SSG（Static Site Generation，静态站点生成）**：一种「在构建时预先把页面渲染成静态 HTML」的建站方式/理念。它只规定「HTML 在什么时刻生产」，不绑定具体技术。
- **VitePress**：遵循 SSG 理念、用 Vite + Vue 实现的一款工具。同类的 SSG 实现还有 VuePress、Docusaurus、MkDocs、Astro、Hugo、Jekyll 等。
用两组熟悉的类比建立直觉：
| 范式 / 规范（抽象） | 具体实现（产品） |
| --- | --- |
| SSG（静态站点生成这种做法） | VitePress / VuePress / Docusaurus / Astro / Hugo |
| MVC（一种架构思想） | Spring MVC（一个实现框架） |
| JDBC（一套接口规范） | MySQL Driver（一个驱动实现） |
准确表述是：「我用 **VitePress** 这个 **SSG 工具** 搭建静态站」。也正因为产物是纯静态文件，它才能直接放到 GitHub Pages 这类只能发文件、不能跑后端的托管上（部署见子模块 05）。
## 三、四种页面渲染范式：给 SSG 一个坐标
四种范式的关键区别只有一个：**HTML 在什么时刻被生产出来**。
| 范式 | HTML 生产时刻 | 首屏 | SEO | 是否需要常驻服务器 |
| --- | --- | --- | --- | --- |
| SPA（客户端渲染） | 浏览器里 JS 跑完后才生成 | 慢，先白屏后渲染 | 弱，爬虫拿到空壳 | 不需要应用服务器，但要静态托管 |
| SSR（服务端实时渲染） | 每次请求时由服务器渲染 | 快 | 好 | 需要 Node 服务 7×24 在线，扛并发 |
| SSG（静态站点生成，VitePress 所属） | 构建/发布时一次性预渲染好 | 极快，HTML 已有内容 | 好 | 不需要，产物是纯文件 |
| 传统 MPA（PHP/JSP 直出） | 每次请求在服务器拼模板 | 取决于后端 | 好 | 需要应用服务器与数据库 |
SSG 与 SSR 用的甚至是同一套服务端渲染能力，差别只在**时机**：SSR 在每个请求上实时渲染 N 次，SSG 在构建时渲染一次并固化成文件。
## 四、Why 深入：为什么内容型站点天然适合 SSG
判断该不该用 SSG，看读写比与时效性：文档、博客、产品手册、知识库都是**读极多、写为零（访客不产生内容）、变更只发生在作者发布时**。把渲染成本从「每次请求」挪到「每次发布」对这类站点是纯赚：
- **构建期算一次，访问期零计算**：发布时跑完构建，之后每个访客拿到同一份静态文件，边缘 CDN 直接回吐，没有应用进程、没有数据库连接。
- **不牺牲时效性**：作者一推送就触发一次新构建，内容更新照样分钟级生效；「静态」指「两次发布之间内容不变」，不是「永远不更新」。
- **反例（不这样会怎样）**：若做成纯 SPA，首屏要等 JS 下载执行后才取数据，白屏且搜索引擎抓到空挂载点；若做成 SSR，则要长期维护一台会崩、会被打、要打补丁的服务器，为「内容几乎不变」的站点付出动态系统的全部代价。
::: info
**一句话**：内容型站点没有「按请求变化」的数据，就没有必要为「按请求渲染」付费——这是选择 SSG（进而选择 VitePress）的根本理由。
:::
## 五、How 概览：VitePress 的技术构成与两种工作模式
VitePress 不是从零造的框架，而是把几件成熟工具按「静态文档」目标粘合起来：
| 组成 | 承担的职责 |
| --- | --- |
| Vite（`1.6.4` 内置 `vite ^5.4`） | 开发服务器、按需编译、生产打包与依赖预构建——VitePress 的底层引擎 |
| Vue 3（内置 `vue ^3.5`） | Markdown 被编译成 Vue 组件；运行时水合与交互；md 中可直接写 Vue |
| markdown-it 及 mdit-vue 插件 | Markdown 解析、frontmatter、标题提取、代码组/容器等扩展 |
| Shiki（内置 `shiki ^2`） | 代码高亮，在构建期直接输出带颜色的静态 HTML |
| MiniSearch（内置 `minisearch ^7`） | 本地全文搜索，索引构建期生成，检索在浏览器内完成 |
它有两种必须区分的工作模式（完整管线见子模块 04）：`vitepress dev` 是开发模式，Vite 起本地服务、按需即时编译、改 md 热更新；`vitepress build` 是生产模式，把每条路由预渲染成静态 HTML 并产出供水合用的 JS。**开发时像 SPA 一样顺滑，交付时是一堆静态文件**，正是 Vite 让这两者共用同一套组件代码。
## 六、同类 SSG 工具选型对比
选型不是比谁「更强」，而是匹配团队既有的语言栈与交互密度：
| 工具 | 技术栈 / 打包 | 机制特点 | 更适合 |
| --- | --- | --- | --- |
| VitePress | Vue 3 + Vite | 运行时极轻，Vite ESM 开发冷启动快；md 即 Vue 组件 | 会 Vue、追求简洁与性能的技术文档 |
| VuePress 2 | Vue 3 + 可插拔构建器（Vite） | 插件/主题生态更庞大，配置层更厚，运行时更重 | 依赖其成熟主题/插件生态的站点 |
| Docusaurus | React + webpack/Rspack | 功能大而全（版本化文档、i18n 开箱即用） | React 团队、需要复杂文档门户 |
| MkDocs（Material） | Python | 纯 Markdown，无前端组件模型，配置即 YAML | 不写前端、Python 背景团队 |
| Astro | 多框架（岛屿架构） | 默认零 JS，按需为交互组件「注水」，概念更多 | 多框架混合、营销+内容一体化 |
机制上最容易被忽略的一点：VitePress 的快主要来自 **Vite 的原生 ESM 开发服务器**——dev 时不预先打包整个站点，浏览器请求到哪个 md 才编译哪个，因此上千页项目冷启动也是秒级。
## 七、易混三兄弟：Vite / VitePress / VuePress 各自的定位
三个名字都带 Vit/Vue，但处在**不同抽象层**，绝不能混用（版本事实截至 2026-10）：
| 名字 | 类别 / 抽象层 | 定位 | 关键事实 |
| --- | --- | --- | --- |
| Vite | 通用前端**构建工具**（dev server + 打包器）；不是框架，更不是建站工具 | 取代 webpack 的下一代工具链：开发时基于浏览器原生 ESM 按需编译、用 esbuild 预构建依赖，冷启动与热更新不随项目变大而变慢；生产用 Rollup 打包 | 独立通用，任何 Vue/React/Svelte/原生 TS 工程都能用；自身最新线已到 `8.x`，而 VitePress `1.6.4` 内部锁定 `vite ^5.4` |
| VitePress | **SSG**（内容型建站框架） | Vue 团队当前的文档站主力方案：在 Vite 之上叠加「Markdown→Vue 组件 + SSG 预渲染 + 默认主题」，约定优先、运行时小、速度快 | 稳定线 `1.6.4`，本知识树主角 |
| VuePress | **SSG**（与 VitePress 平级） | VitePress 的同门前身：2018 年尤雨溪为编写 Vue 官方文档而创建；插件/主题生态庞大、可扩展性强，是「功能完备的框架」，配置层更厚 | `1.x` 基于 webpack + Vue 2，仍是 npm 的 `latest`（`1.9.10`），存量维护；`2.x` 用 Vue 3 重写、构建器可插 Vite，但长期停在 RC（最新 `2.0.0-rc.31`，2026-07），未发稳定版 |
三者的层级与依赖关系：
```plain text
内容/应用层    VitePress（轻量 SSG，本主题）      VuePress（生态完备的 SSG）
                      │ 构建于                    │ 2.x 可挂 Vite 作为 bundler
框架层              Vue 3（两者共用）
构建工具层           Vite（dev server + Rollup 生产构建）
```
三句话收口：
- **Vite 与另两者不是同类**：Vite 是底层构建工具，VitePress/VuePress 是建在它（或 webpack）之上的 SSG；类似「webpack 之于 VuePress 1 / 老式 Vue CLI 工程」。
- **VitePress 与 VuePress 平级**，是同一作者的两代方案：VuePress 是前身、生态重，VitePress 是精神续作、轻量快；Vue 团队对新项目首推 VitePress。
- **选型口径**：做普通 Web 应用/组件库要构建工具 → 用 Vite；新建文档/博客/知识库 → VitePress；已重度依赖 VuePress 特定插件/主题或维护存量站 → 才保留 VuePress，新项目没有理由选一个多年 RC 的 2.x。
::: warning
**高频误区**：不要把「Vite」当成「VitePress」的简称——前者是通用构建工具（也用来构建 React 项目），后者是用它构建的文档站框架；也不要以为 VuePress 2 已是稳定版。
:::
## 八、JAMStack 与「无后端」的准确边界
VitePress 站点常被归入 JAMStack（JavaScript、API、Markup）。要澄清一个误解：**静态不等于没有交互**。动态能力来自「构建期预处理」与「第三方 API」两个方向，而不是一台自己的应用服务器：
| 传统上依赖后端的能力 | 静态站的实现方式 |
| --- | --- |
| 内容存储与查询 | 构建期把 Markdown 固化进 HTML/索引，Git 仓库承担版本化存储 |
| 全文搜索 | 构建期生成 MiniSearch 索引，浏览器本地检索 |
| 评论 | 第三方服务（如基于 GitHub Discussions 的 Giscus） |
| 统计/表单 | 第三方脚本或 Serverless 函数 |
边界在于：一旦需要**服务端持有状态**（用户登录、写数据库、权限校验、实时数据聚合），纯 SSG 就不够了，需要补 BFF 或 Serverless。
## 九、When not：不适用 VitePress 的场景
- 强登录态、按用户返回不同内容的应用（应选 SSR/普通 Web 应用）。
- 高频实时数据（行情、监控大盘），页面内容秒级变化，预渲染没有意义。
- 团队完全不碰 Node/前端，只想要「丢 Markdown 就出页面」，MkDocs 这类零 JS 模型心智更轻。
## 十、实战场景
### 场景 1：团队知识库该用 Confluence/WordPress 还是 VitePress
现象：团队在 SaaS 知识库与自建站间犹豫。决策路径：先看内容是否以「发布」为主、能否接受 Git 工作流，再算成本。结论：技术团队的文档读多写少、希望随代码版本演进、要完全掌控样式与数据可迁移，VitePress 加免费静态托管在成本、可维护性、可迁移性上全面占优；非技术同学频繁在线富文本协作、需要细粒度权限审批，则 SaaS 知识库更合适。
### 场景 2：已有 Vue 技术栈，文档站要不要改用 Docusaurus
不要为「功能多」跨技术栈引入 React 全家桶。文档站要写自定义组件时，VitePress 可直接复用团队的 Vue 组件与调试经验；引入 Docusaurus 等于为一个静态站养两套前端工具链。只有当你强依赖 Docusaurus 独有的版本化/多版本门户且团队熟 React 时才反转结论。
### 场景 3：存量 VuePress 站点要不要迁 VitePress
先看是否真用到了 VuePress 专属的重型插件/主题：若只是文档与默认主题，迁移收益明显（更快的 dev、更小的运行时、Vue 团队长期投入），主要成本是配置项与主题 API 的改写；若深度绑定 VuePress 插件生态，则留在 VuePress 1.x 稳定线、观望 2.x 稳定版，比为迁移重写一套插件更划算。
## 十一、关键问题思考
1. **[高频] 概念题：用一句话说清 VitePress 是什么（What）。** 它是 Vue 团队出品的静态站点生成器：用 Markdown 写内容，基于 Vite + Vue 在构建时把页面预渲染成纯静态 HTML/CSS/JS，交付一个免服务器、首屏快、SEO 好的内容型网站。
2. **[高频] 辨析题：VitePress 和 SSG 是什么关系？** SSG 是「构建时预渲染静态 HTML」的一类架构范式，VitePress 是该范式用 Vite + Vue 实现的一款具体工具；如同 MVC 之于 Spring MVC，是「方法论与产品」而非并列关系。同类实现还有 VuePress、Docusaurus、Astro、Hugo。
3. **[高频] 辨析题：Vite、VitePress、VuePress 三个名字什么关系？** 处在不同层：Vite 是通用前端构建工具（原生 ESM dev server + Rollup 生产打包），VitePress 与 VuePress 是平级的两个 SSG，都基于 Vue、都可用 Vite 构建。VitePress 是 Vue 团队当前主力的轻量方案；VuePress 是其同门前身，`1.x` 基于 webpack + Vue 2 仍维护，`2.x` 用 Vue 3 重写但长期处于 RC。依赖方向是「SSG 建在 Vite 之上」，类似 webpack 之于 VuePress 1。
4. **[高频] 原理题：为什么文档站用 VitePress/SSG 几乎没有代价（Why）？** 文档读多写少、访客不产生内容，变化只发生在发布时。把渲染从「每次请求」挪到「每次发布」只做一次，之后流量全部由 CDN 文件缓存承担；推送即重建所以时效仍是分钟级，又不用养服务器。
5. **[高频] 原理题：它是怎么把 Markdown 变成网站的（How）？** dev 时 Vite 起本地 ESM 服务按需即时编译；build 时 markdown-it 解析 md、编译为 Vue 组件，再用服务端渲染逐路由预渲染成 HTML，浏览器加载同构 JS 后水合。细节见子模块 04。
6. **[高频] 场景题：什么情况下该用、什么情况下不该用（When）？** 该用：技术文档、知识库、博客、手册等内容型站点。不该用：强登录态与按用户渲染、秒级变化的实时数据、或团队完全不接受 Node/Git 工作流（后者可考虑 MkDocs）。
7. **[高频] 辨析题：SSG、SSR、SPA 的核心区别是什么？** 看 HTML 的生产时刻：SPA 在浏览器执行 JS 后生成，首屏白屏、SEO 弱；SSR 每次请求由服务器实时渲染，首屏快但需常驻服务；SSG 在构建发布时一次性预渲染成文件，访问直接取文件，首屏快、SEO 好且无需服务器。SSG 与 SSR 用同一套渲染能力，差别只在时机与是否固化成文件。
8. **[中频] 辨析题：静态站点是不是就不能有搜索、评论这些动态功能？** 不是。动态能力不必来自自有后端：搜索用构建期生成索引 + 浏览器本地 MiniSearch，评论/统计用第三方 API（如 Giscus），真正需要服务端持状态时才补 Serverless。它省掉的是自建的有状态应用服务器。
9. **[中频] 原理题：为什么 SSG 对 SEO 友好而纯 SPA 不友好？** SSG 直接下发含完整正文的 HTML，爬虫无需执行 JS 即可读到内容；SPA 首屏只有空挂载点与一个 JS 包，依赖爬虫执行 JS 后才有内容，抓取时序与兼容性都更差。
